Why OSWM created this format

The routing demo needs connectivity and costs, whereas the map needs drawable geometry. OSWM’s custom .oswmg file is a prebuilt binary graph for the first task. Python prepares the topology, profile costs and spatial index once during node generation. A static web server can then deliver that graph directly to a JavaScript worker, alongside separate PMTiles for drawing the network.

From processed data to bytes

  1. Prepare evidence. The generation pipeline reads processed sidewalks, crossings and other footways, associates nearby crossing/kerb evidence, resolves slope and calculates separate forward and backward accessibility grades.
  2. Assign node IDs. Existing geometry vertices are merged by rounded coordinate keys using a tolerance of 1e-05 degrees. This is an angular tolerance: approximately 1.1 m north–south, with longitude distance depending on latitude. The last raw coordinate seen for a key is retained as its representative. IDs are dense local array positions, not OSM IDs.
  3. Create directed edges. Each consecutive pair of distinct vertex IDs becomes two directed entries. Their profile costs can differ; an excluded direction has positive Infinity as its weight. A distance edge uses its haversine length. Accessibility edges use length × multiplier plus the feature event penalty’s proportional share.
  4. Arrange outgoing edges. Entries are sorted by source ID, then target ID. The writer stores adjacency offsets, targets and one block of costs per profile. Duplicate source–target entries use the last feature encountered, preserving the existing topology reducer’s behaviour.
  5. Index segments. Unique undirected node pairs form a snapping segment list. A bounded uniform grid stores references to every segment whose bounding box overlaps a cell. This is a conservative candidate index, not a second routing network.
  6. Serialize and audit. The writer computes absolute byte offsets, writes a fixed header followed by contiguous arrays, atomically replaces the file and records SHA-256 and counts in the generated metadata. Profile IDs and their ordering are kept in profiles.json.

Lines that merely cross geometrically are not automatically connected; this builder uses existing rounded vertices. The binary graph inherits the processed network’s connectivity.

Internal structure, byte by byte

All multibyte numbers use little-endian order. The header starts at byte zero, followed immediately by the arrays below. Header array pointers are absolute byte offsets from the start of the file; adjacency and cell offsets are array indices, not byte addresses.

Float64 takes 8 bytes, Float32 and Uint32 take 4 bytes. The arrays contain no repeated feature/property objects or coordinate strings. Positive IEEE-754 Infinity is a blocked weight. Profile names, labels, speeds, rules and original source attributes are not embedded in these arrays.

Total bytes = 192 + 16V + 4(V + 1) + 4E + 4PE + 8S + 4(C + 1) + 4M

The current layout places the Float64 arrays first at aligned offsets. The browser uses DataView for header fields and native typed-array views into the fetched ArrayBuffer on little-endian machines. That avoids copying each payload array into JavaScript objects; downloading the buffer and allocating search state still use memory.

A worked three-node example

Consider A (node 0) at [0, 0], B (node 1) at [0.001, 0], and C (node 2) at [0.002, 0]. There are two sidewalk segments. The example assigns explicit directional grades to demonstrate encoding; these are illustrative inputs, not a field assessment. The values and byte offsets on this page are decoded from a file generated by the actual Python writer.

profile order:      [distance, wheelchair]
adjacency_offsets:  [0, 1, 3, 4]
targets:            [1, 0, 2, 1]

Node B’s outgoing entries occupy positions 1 through 2: start at adjacency_offsets[1] = 1, stop before adjacency_offsets[2] = 3. Their targets are A and C. This arrangement is called compressed sparse row (CSR); the source node is implicit in the offset range.

How the browser uses it

Load once per worker

The client reads profiles.json and gives its graph URL and profile order to a Web Worker. The URL is versioned with the recorded graph checksum for cache invalidation. The worker checks magic, schema, header size, array offsets/truncation and profile count, then creates typed-array views. These are compatibility checks, not a full cryptographic verification of the downloaded graph.

Snap a click

The worker starts in the click’s grid cell and expands through neighbouring cells. It projects onto candidate segments, filters out unusable profile positions, and stops when unvisited cells cannot offer a nearer point or are beyond the 100 m access radius. Per-search marks avoid testing a segment repeatedly when it appears in several cells. The result records a segment ID and fraction along it, rather than requiring the click to coincide with an existing node.

Find a route

A* searches outgoing adjacency ranges using a min-heap. The heuristic is a conservative straight-line distance scaled for the profile, with a small margin for Float32 rounding; an unavailable heuristic falls back to zero. Nonfinite weights are skipped. Endpoint partial-edge costs connect snapped positions to their adjacent nodes, and the resulting predecessor chain reconstructs route coordinates. Distances and predecessors are temporary per-search arrays.

Calculate isochrones

A bounded Dijkstra search explores outward while accumulated profile cost is within the largest time budget. It finds reachable nodes and partial segments for each cutoff. Those segments are buffered/rasterized on a shared local grid and converted to cumulative polygons. Network search and polygon construction are separate work; large budgets or many bands can make polygonization expensive.

Where the speed comes from

Design choiceWork it saves or moves
Offline graph constructionTopology, directional costs and spatial indexing are prepared during publication instead of on each browser load.
Binary numbers and dense IDsThe browser avoids parsing coordinate strings and rebuilding a graph from feature/property objects.
Contiguous typed arraysOutgoing edges and profile costs are addressed by array position; profile changes reuse the topology.
Uniform-grid snapping indexNearby candidate segments are examined instead of scanning every feature for every click.
A* plus min-heapA geographic lower bound can reduce exploration compared with an uninformed full-graph search.
Web WorkerSearch work runs off the UI thread, allowing map interaction to remain responsive; threading does not itself reduce CPU work.
Separate PMTiles displayMap drawing can stream tiles independently of the analytical graph; the router does not fetch GeoParquet to calculate a path.

Compact storage is not compression: the current .oswmg payload is uncompressed binary and can also benefit from HTTP compression. “Fast” describes these design choices, not a fixed latency guarantee. A competing graph library can still win a particular query; the recorded benchmark below measures this explicitly.

Seed 20261110; 30 vertex pairs and 8 click positions per profile, repeated 3 times after 3 route and 2 snapping warm-ups. Each engine runs in a fresh process. p95 is a sample percentile, not a browser responsiveness guarantee.

Route endpoints are existing vertices in the largest distance-profile component. The four profiles receive the same pairs, including pairs that accessibility rules may disconnect. Costs and directional exclusions are identical; cost agreement allows 0.05 equivalent metres or 0.001% relative error. Snapping uses the same 100 m radius and outward eligibility, allowing 0.1 m distance disagreement because Turf uses great-circle geometry and OSWM uses a local planar projection.

Scope matters. Turf’s nearest-point operation is measured both as a full scan and with an RBush spatial index. Turf’s shortestPath solves obstacle avoidance on a grid, rather than this preweighted pedestrian graph, so it receives no network-routing score. GeoJSON Path Finder and ngraph.path are the network-routing comparators. Search timings use common vertex endpoints; full click-to-route UI latency and arbitrary partial-edge attachment are not measured. OSWM also constructs its route geometry and distance; ngraph’s timed operation returns node IDs.

Correctness finding: GeoJSON Path Finder 2.1.0 can discard a cheaper parallel corridor during graph compaction. The benchmark includes a small regression fixture where it returns cost 800 while OSWM and ngraph preserve a cost-300 path. The mismatch columns report affected Milan queries; its timings therefore do not establish a speed comparison between equally correct solutions. ngraph provides the independent routing-cost cross-check.

The figures may favour different engines on different tasks. They are one controlled dataset/run, not a universal ranking. Approximate process memory deltas and route outcomes are available in the raw report; they exclude the common validation graph and are not browser peak-RAM measurements.

Tradeoffs and compatibility

The full graph is fetched for a node, so initial transfer and RAM still grow with network size and number of profiles. Costs use Float32 precision, while coordinates use Float64. The snapping grid adds some duplicated segment references to accelerate searches. Disconnected components can force more search work, and A* has no universal bound on the fraction of the graph it must visit.

This is an OSWM-specific runtime format, not a replacement for the node’s analytical GeoParquet or a general geospatial exchange standard. The companion profile order must match the graph. The current worker accepts schema 2; a layout change needs a coordinated writer/reader version update. Native payload views assume a little-endian browser platform.
